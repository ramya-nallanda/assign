# REVIEW.md

Defects found in the starter `app/main.py`. "Notice" = how it shows up; every example below was run against the
original starter, not guessed.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | `punch_in.replace(hour=9, minute=30)` builds the shift start in the punch-in's *own* time zone (UTC / server-local), not IST. | Punch-in 04:35Z (= 10:05 IST), shift 09:30 returns **0**, should be 35. | Shift start is built as an IST datetime for the attendance date, then compared as instants. |
| 2 | `compute_late_minutes` | Floors to whole minutes *then* tests `> 10`, so the "strictly more than 10:00" boundary is lost. Sub-second noise is also not truncated (R1). | 09:40:01 returns **0**, R2 says 10. | Compare in seconds (`> 600`), then floor to minutes; instants truncated to whole seconds on input. |
| 3 | `compute_late_minutes` / `compute_overtime` | No overnight-shift support: start/end are taken on the punch's calendar day. | Shift 22:00-06:00, out 06:40 next day gives overtime **1480**, should be 40. | `shift_bounds()` puts an overnight `shift_end` on the next day; `attendance_date()` implements R1's "earlier than shift_end = previous day". |
| 4 | `compute_work_hours` | Python `round()` on a float: not half-up (R4) and float-error prone. | 9630 s = 2.675 h returns **2.67**, should be 2.68. | `Decimal(seconds)/3600`, `quantize(0.01, ROUND_HALF_UP)`. |
| 5 | `compute_overtime` | No 30-minute minimum (R3). Also never called, and there is no `half_day` rule (R5) at all. | Punch-out 18:35 on a 18:30 shift returns **5**, should be 0. | Minimum added; `compute_half_day()` added; all four derived fields come from one `derived_fields()`. |
| 6 | `EmployeeIn` | No validation: any string is accepted for code, email, shift times, `joined_on`; `shift_start == shift_end` allowed. | `{"emp_code":"x","email":"nope","shift_start":"25:99","joined_on":"soon"}` returns 201, should be 422. | Pattern/length constraints from the contract, real-date check, shift_start != shift_end validator. |
| 7 | `create_employee` | Check-then-insert with no unique index: two parallel creates both pass the `find_one`. Also `created_at = datetime.now()` is naive *local* time and is returned as an ISO string, not epoch ms. | Parallel POSTs with one code give two 201s and duplicate rows. | Unique index on `emp_code`; insert and catch `DuplicateKeyError` -> 409. `created_at` is UTC and serialised as epoch ms. |
| 8 | `list_employees` | `skip = page * page_size` (page 1 skips the first page); `total` is `count_documents({})` and ignores the department filter; no sort, so pages are unstable; `page`/`page_size` unbounded. | Page 1 returns the second page; `?department=X` shows the whole-company total; `page=-1` gives a negative skip -> pymongo `ValueError` -> 500. | `(page-1)*page_size`, count uses the same filter, sort by `emp_code`, `page>=1`, `1<=page_size<=100` (422 otherwise). |
| 9 | `punch_in` | Unknown employee: `emp` is `None`, `emp["shift_start"]` raises `TypeError`. | POST with an unknown `emp_code` returns **500**, contract says 404. | `get_employee_or_404()`. |
| 10 | `punch_in` | `datetime.fromtimestamp(ms/1000)` is naive *server-local* time, so `date` is the server's calendar date, not IST (R1), and PyMongo stores naive values as UTC, so the stored instant is wrong unless the server is UTC. Milliseconds are not truncated. | On a UTC server 23:00Z (04:30 IST next day) is filed under the wrong date. | `ms -> aware UTC datetime` truncated to seconds; date derived in IST by `attendance_date()`. Mongo client is `tz_aware=True`. |
| 11 | `PunchInIn` | `punched_at: Optional[int]` lax-coerces `"1783312500000"` and `1.0`, and accepts seconds-looking or negative values; `status: str` accepts `ABSENT`, `banana`. | `punched_at: 1783312500` creates a record dated 1970; `status: "ABSENT"` is stored with a punch-in. | `StrictInt` in [1e11, 4102444800000]; `status` is `Literal[PRESENT, WFH, ON_DUTY]`. |
| 12 | `punch_in` | Check-then-insert race (no unique index): two simultaneous requests both pass `find_one` and both insert. | Two parallel identical requests give two 201s. | Unique `(emp_code, date)` index; insert, catch `DuplicateKeyError` -> 409. |
| 13 | `punch_in`, `list_attendance` | Response leaks the internal `_id` as `id`, and returns raw datetimes (ISO strings) instead of epoch ms. | `id` in every body; `punch_in` is `"2026-07-06T..."`. | `record_out()` builds the contract shape; `_id` never leaves, instants are epoch ms. |
| 14 | `list_attendance` | `list(find(q))` loads every matching document and sorts/paginates in Python. | ~100k records: seconds and hundreds of MB per request. | `find().sort().skip().limit()` in MongoDB, backed by indexes; `count_documents` only when filtered. |
| 15 | `list_attendance` | Sorted by `date` only (ties arbitrary; contract says then `emp_code` asc). No validation: `date_from > date_to` returns an empty page, bad dates / bad `status` are accepted, `page=0`/negative slice wrongly. | `?date_from=2026-07-09&date_to=2026-07-01` returns 200, should be 422. | Strict date parsing, range check -> 422, `status` enum, `date desc, emp_code asc` sort. |
| 16 | `list_attendance` | Legacy documents without `half_day` / `history` come back without those fields. | Sample doc #9 has no `half_day`. | `record_out()` defaults missing values (`false`, `[]`, 0). |
| 17 | `/health` | Always returns ok, never touches MongoDB. | Stop Mongo: still 200, contract says 503. | Pings Mongo, 503 on failure. |
| 18 | module setup | `MongoClient` without `tz_aware`, no indexes created anywhere, default 30 s server-selection timeout. | Naive datetimes everywhere; every query is a collection scan. | `tz_aware=True`, 5 s timeout, idempotent `ensure_indexes()` at startup (retried from `/health` if Mongo was late). |

**Looked at and judged fine**
- `IST = timezone(timedelta(hours=5, minutes=30))` is correct (no DST in IST), so I reused it.
- `load_dotenv()` does not override variables that are already set, which is exactly the "real environment wins" rule.
- Sync `def` endpoints run in FastAPI's thread pool and `MongoClient` is thread-safe, so a module-level client is fine.
- `201` on both create endpoints is right; `doc.pop("_id")` after `insert_one` was needed (PyMongo mutates the dict) and is replaced by explicit serialisation.
